# TOAP A/B Study (proj1 baseline vs proj2 TOAP)

A paired A/B benchmark of TOAP's reference-minimization against a naive full-context baseline, using
**real isolated Claude subagents** as the LLM and **runtime-reported token usage** as the measurement.

## The design (and why "same exact prompts" would be wrong)

The two arms run the **same task pipeline** (extractor → analyst → writer) over the **same documents**
with the **same role instructions**, the **same model** (Claude subagents), and the **same independent
judge**. The ONLY thing that varies is **context assembly** — and that necessarily makes the prompts
differ. (If both arms used byte-identical prompts, token consumption would be identical and there would
be nothing to measure: changing the prompt *is* what TOAP does.)

- **proj1_baseline:** each downstream agent's prompt = full document + all prior verbatim outputs.
- **proj2_toap:** each downstream agent's prompt = only the distilled upstream output it needs
  (analyst ← facts; writer ← analysis). This is what TOAP's `CTX:n` references enable.

Prompts are **generated by `harness.py`** from the scenario + verbatim upstream outputs — not hand-typed
— which removes "the author tweaked the prompt" doubt.

## What is measured, and how to verify it

Each pipeline stage is one isolated subagent (`tool_uses=0`). For every call we commit the **verbatim
prompt, verbatim output, runtime `subagent_tokens`, and agent-id** in `runs/`. Two metrics:

1. **Reproducible (tiktoken):** `analyze.py` re-tokenizes the stored prompts+outputs — anyone recomputes
   this exactly from the records. This is the defensible number.
2. **Runtime (`subagent_tokens` net of a calibration overhead):** the real model usage, but a single
   nondeterministic sample per call, not re-derivable. Reported as a cross-reference.

The two agree closely per scenario, which is the point: the runtime numbers can't be fabricated when a
deterministic re-tokenization of the committed text reproduces the same reduction.

## Results so far (n = 2 scenarios)

| scenario | tiktoken pipeline | tiktoken downstream | runtime pipeline | runtime downstream | accuracy (judge) |
|---|---|---|---|---|---|
| 01 incident postmortem | 1.40× | 1.65× | 1.40× | 1.65× | 4/4 vs 4/4 |
| 02 support escalation | 1.52× | 1.82× | 1.56× | 1.89× | 4/4 vs 4/4 |
| **aggregate (mean)** | **1.46×** | **1.74×** | **1.48×** | **1.77×** | **parity** |

Range across scenarios: pipeline 1.40–1.52×, downstream 1.65–1.89×. Accuracy parity held in both
(independent judge, both arms cover all rubric items). The extractor reads the full document in both
arms, so the *overall* number is diluted; the *downstream* number is where TOAP acts.

## Run it / extend it

```powershell
# generate a prompt (proves prompts are code-generated, not hand-typed)
python benchmark/ab_study/harness.py benchmark/ab_study/scenarios/scenario_02_support.json extractor

# aggregate all committed runs
python benchmark/ab_study/analyze.py
```

To add a scenario: drop a `scenarios/scenario_NN_*.json` (document + rubric), run each stage as a
subagent with harness-generated prompts, save the verbatim record to `runs/scenario_NN_*.json`, and
`analyze.py` will fold it into the aggregate. More scenarios tighten the estimate.

## Honest limitations (for any write-up)

1. **Single model family** (Claude). Needs ≥2 independent models to generalize.
2. **n = 2** so far; single sample per call. Add scenarios + repeats for variance/CIs.
3. **Overhead** subtracted using one calibration, reused across scenarios (may drift).
4. **Judge** is the same model family (fresh, blind A/B) — better than self-judging in-context, not a
   fully independent evaluator.
5. **Baseline** is the naive transcript-accumulation pattern; a hand-tuned baseline could also minimize
   context — which is exactly what TOAP systematizes.
6. Savings are in **prompt/coordination tokens**, not the model's output tokens.
