# TOAP Engineering Decisions

This document records implementation-shaping decisions. Add to it whenever the protocol or architecture changes in a way future contributors need to understand.

## Decision 1 - Broker-Derived Source Identity

The V1 wire frame is:

```text
TYPE|MSG_ID|TARGET|PAYLOAD
```

It does not include a trusted `SRC` field. The broker derives source identity from the connection/session.

Reason: a client-claimed source field is easy to spoof unless every message is signed. Connection-bound identity is simpler for V1 and keeps routing, ACL checks, logs, and rate limits aligned with broker state.

## Decision 2 - Function-Style Payloads

Payloads use:

```text
OP(args)?key=value&key=value
```

Reason: the earlier `SUM:CTX:42` shape is ambiguous because `CTX:42` itself contains a colon. Function-style payloads make positional arguments and options explicit.

## Decision 3 - Trust Is Policy-Derived

Agents may request identity and capabilities during `SYN`, but the broker decides final trust level.

Reason: self-declared trust is not security. The broker must derive trust from configuration, allowlists, credentials, or future authentication mechanisms.

## Decision 4 - Taint Instead Of Broad Content Rejection

TOAP tracks untrusted content as tainted data instead of rejecting ordinary documents that contain suspicious-looking strings.

Reason: code, SQL, markdown, HTML, logs, and prompt text are legitimate content in many workflows. Rejecting them by pattern would make the protocol unreliable and still would not provide strong security.

## Decision 5 - Measured Claims Only

Numeric savings are not accepted as project facts until generated by the benchmark suite.

Reason: early targets are useful for direction, but publishing them as results would make the project less credible. `docs/claims.md` is the claims ledger.

## Decision 6 - Numeric Context IDs First

The first implementation uses numeric context IDs as canonical keys.

Reason: numeric IDs are simpler to validate, store, benchmark, and secure. Named aliases can be added later as metadata that maps to numeric IDs.

## Decision 7 - CMake Skeleton Before Targets

Phase 1 includes a root CMake project with no implementation targets.

Reason: this validates the local C++ toolchain and gives later phases a stable place to add protocol, broker, storage, and test targets without moving project roots.

## Decision 8 - Assertion-Based Protocol Tests First

Phase 2 uses a small C++ test executable with standard `assert` instead of adding Google Test immediately.

Reason: the protocol core is still small, and avoiding an external test dependency keeps early builds simple. A richer test framework can be added when broker and storage integration tests need fixtures.

## Decision 9 - Static GCC Runtime For Windows Tests

The protocol test executable statically links the GCC runtime on Windows GNU builds.

Reason: CTest launched the executable without the MinGW runtime DLLs on PATH. Static runtime linking makes local test execution stable without requiring users to edit environment variables.
